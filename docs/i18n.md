# Infrastructure i18n

Cette première étape installe un socle i18n léger et typé, sans modifier le rendu, les formulaires ou les routes existantes. Elle n'ajoute aucune dépendance : le chargement dynamique des dictionnaires repose sur TypeScript et Next.js.

## Langues

| Locale | Libellé | Drapeau | Langue HTML cible |
| --- | --- | --- | --- |
| `fr` | Français | 🇫🇷 | `fr-HT` |
| `en` | English | 🇺🇸 | `en` |
| `es` | Español | 🇪🇸 | `es` |

La langue par défaut est `fr`. Les constantes, le type `Locale`, les libellés et `isValidLocale` sont définis dans `src/i18n/locales.ts`.

## Structure

```txt
src/i18n/
  index.ts
  locales.ts
  routing.ts
  messages.ts
  messages/
    fr.json
    en.json
    es.json
```

- `locales.ts` est la source de vérité des locales.
- `routing.ts` résout une locale et construit un chemin préfixé en conservant query string et ancre.
- `messages.ts` charge dynamiquement un seul dictionnaire et expose son type.
- Les JSON contiennent les namespaces initiaux `common`, `navigation`, `footer`, `home`, `services`, `contact`, `consultation`, `academy` et `seo`.
- `index.ts` fournit le point d'entrée public du module.

## Utilisation

```ts
import { getLocalizedPath, getMessages, isValidLocale } from "@/i18n";

const locale = isValidLocale(candidate) ? candidate : "fr";
const messages = await getMessages(locale);
const servicesUrl = getLocalizedPath("/services?source=home", locale);
```

`getLocalizedPath` prépare les URLs `/fr`, `/en` et `/es`, mais ne garantit pas que la route cible est déjà publiée. Le sélecteur conserve actuellement l'accueil localisé et revient vers `/{locale}` depuis les autres pages ; un registre de disponibilité remplacera cette règle au fil des migrations.

## Ajouter ou modifier une traduction

1. Choisir le namespace fonctionnel approprié.
2. Ajouter la même clé aux trois JSON ; le fichier français définit la forme TypeScript attendue par les autres chargeurs.
3. Employer une clé sémantique telle que `navigation.home`, jamais la phrase française comme clé.
4. Garder hors des dictionnaires les identifiants métier, slugs, endpoints, noms de champs et valeurs envoyées aux API.
5. Exécuter `npm run lint` et `npm run build`. Le build TypeScript détecte notamment une structure incompatible dans un dictionnaire chargé.

Pour ajouter une langue, il faudra ajouter son code à `locales`, sa configuration dans `localeConfig`, son JSON, puis son loader dans `messages.ts`. Une future PR devra également déclarer ses routes et ses metadata SEO.

## État de couverture des traductions

La cause de la couverture partielle était double : seules les routes d’index
localisées transmettaient la locale à leurs composants, tandis que les sections
secondaires et les données éditoriales continuaient à consommer directement des
chaînes françaises. Le registre du sélecteur de langue ne connaissait pas non
plus les routes de détail.

### Entièrement traduit (interface publique)

- chrome public : navbar, sélecteurs desktop/mobile, footer et newsletter ;
- accueil : hero, domaines, méthode, Academy, partenariats, consultation,
  témoignages et actualités ;
- Services : index, filtres, cartes, données statiques et fiches détaillées ;
- Contact et réservation de consultation : labels, aides, validations et états
  de soumission, sans changement des noms de champs ni des contrats API ;
- Academy publique : catalogue et interface des fiches de cours ;
- Actualités : liste, cartes, interface des articles et quatre articles de repli
  statiques, avec routes FR/EN/ES ;
- CTA, boutons et liens des familles de pages ci-dessus.

Les routes historiques françaises non préfixées sont conservées. Les variantes
`/fr`, `/en` et `/es` existent pour les index et pour les détails Services,
Articles et Academy. Le sélecteur conserve désormais la famille et le slug lors
d’un changement de langue sur ces routes.

### Contenus dynamiques et couverture éditoriale

Les articles et cours provenant de Supabase ne disposent actuellement que de
champs monolingues. Leur **interface** est traduite, mais leur titre, extrait,
description, programme ou contenu éditorial utilise le français comme fallback.
La logique Supabase et le schéma n’ont volontairement pas été modifiés. Les
articles statiques livrés avec l’application possèdent des traductions
éditoriales contrôlées en anglais et en espagnol.

Pour compléter les contenus Supabase, la solution recommandée est un champ
`translations` JSONB indexé par locale ou une table `article_translations` /
`course_translations` reliée à l’enregistrement source. Cette évolution doit
être accompagnée d’un workflow éditorial ; aucune traduction automatique ne
doit être effectuée côté client.

### Stratégie de fallback

1. utiliser la traduction demandée lorsqu’elle existe ;
2. utiliser la valeur française contrôlée lorsqu’elle manque ;
3. utiliser un libellé générique traduit pour les valeurs optionnelles ;
4. ne jamais rendre une clé, `undefined`, `null` ou un objet brut.

L’admin, le CRM, l’espace étudiant privé, les emails transactionnels, les
paiements et les contrats backend restent volontairement hors périmètre.

## Limites actuelles

- Les routes publiques historiques restent volontairement non préfixées et continuent à fonctionner telles quelles.
- Les accueils, index prioritaires et principales pages de détail existent sous `/fr`, `/en` et `/es`. Les variantes EN/ES restent temporairement `noindex` tant que tous les contenus Supabase n’ont pas reçu de traduction éditoriale.
- Les dictionnaires alimentent le chrome, les principaux textes visibles, les formulaires publics essentiels et leurs metadata ; les contenus éditoriaux longs restent partiellement en français.
- `<html lang>`, canonical, Open Graph, sitemap et `hreflang` restent ceux du site français actuel.
- Il n'y a pas encore de middleware de détection. Le sélecteur mémorise toutefois le choix dans `NEXT_LOCALE` pour préparer cette future détection.
- Les contenus éditoriaux Supabase (articles et cours) n'ont pas de modèle de traduction et ne sont pas modifiés.

## Prochaines étapes recommandées

- ajouter des traductions éditoriales aux cours et articles gérés dans Supabase ;
- localiser les pages légales après validation juridique ;
- ajouter `hreflang`, canonical et sitemap localisés avant d’autoriser
  l’indexation EN/ES ;
- instrumenter un contrôle CI comparant la forme des dictionnaires et signalant
  les fallbacks éditoriaux.

Les variantes EN/ES restent `noindex` pendant cette phase de contenu partiellement traduit. Leur indexation ne devra être activée qu'après traduction du contenu principal, ajout de `<html lang>`, canonical et `hreflang` cohérents.

## Prochaines PR

1. Piloter `<html lang>` par locale sans capturer `/admin`, `/api` ou les espaces privés.
2. Étendre le registre des équivalences à mesure que les pages détaillées sont réellement publiées.
3. Traduire progressivement les sections secondaires de l'accueil et les fiches Services avec validation éditoriale agricole.
4. Concevoir séparément la traduction des articles et cours venant de Supabase.
5. Ajouter canonical localisés, `hreflang`, Open Graph, sitemap et robots lorsque les variantes sont publiées.

L'admin, le CRM, Academy privée, les emails, Supabase et les contrats des formulaires restent hors périmètre.
